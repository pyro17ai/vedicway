# Технические требования к UI натальной карты на базе PyJHora MCP

Версия исследования: 16 июля 2026 года  
Область: только активный PyJHora MCP, его текущий локальный checkout и точный GitHub-репозиторий  
Целевой формат карты: только южноиндийская South Indian chart, фиксированная сетка знаков  
Контрольные данные: Москва, 16 октября 2006 года, 13:30, числовой UTC-сдвиг 4.0, аянамша LAHIRI

## 1. Решение, которое UI обязан принять

Для отрисовки D1 приложение должно использовать только результат **get_rasi_chart**. Этот tool прямо помечает ответ как D1 (Rasi / Birth Chart), возвращает асцендент и готовый список планет с rasi_index, долготой, Nakshatra и Pada. Его результат служит единственным источником для квадратной South Indian grid и для таблицы положений на вкладке карты.

После исправления MCP **get_planet_positions** использует тот же PyJHora-источник `charts.rasi_chart`, что и **get_rasi_chart**. Оба ответа проходят регрессионное сравнение по девяти классическим планетам и асценденту. Для сетки и основной таблицы UI всё равно принимает канонический snapshot **get_rasi_chart**, а **get_planet_positions** оставляет диагностическим и совместимым источником.

Требование жёсткое: UI не строит западный круг, северную ромбовидную схему или восточную альтернативную сетку. Южноиндийская схема задаётся фиксированными ячейками знаков. Лагна и планеты попадают в ячейки по rasi_index, а номера домов отображаются отдельным слоем с указанием источника.

Живой inspect видит 22 tools, 0 prompts и 0 resources. В режиме stdio сервер запускается командой FastMCP run для server.py. В режиме HTTP main() слушает 0.0.0.0, порт из переменной PORT или 8000. Если задана API_KEY, включается Bearer-проверка через StaticTokenVerifier; без API_KEY авторизация отключена.

В корне MCP уже были незакоммиченные изменения пользователя в исходниках, README, конфигурации и тестах. Все результаты ниже относятся к этому текущему working tree, а не к чистому состоянию Git HEAD. В активном локальном проекте используется Python 3.11.15, тогда как README точного GitHub-репозитория заявляет Python 3.12+; это расхождение нужно устранить в документации и deployment-контракте.

Для расчётов нужны файлы Swiss Ephemeris с расширением .se1 в jhora/data/ephe/. В активном .venv311 найден `seplm48.se1`; MCP теперь явно проверяет этот каталог и задаёт Swiss Ephemeris путь перед расчётом. Контрольный вызов `samvatsara` в свежем процессе возвращает значение без ошибки. UI всё равно показывает частичный результат и диагностику эфемеридного окружения, если отдельное поле расчёта упадёт.

## 3. Входной контракт рождения

Модель рождения состоит из place, date_time и ayanamsa. Place требует name, latitude, longitude и timezone. timezone передаётся как число UTC-сдвига от -14 до 14, а не как IANA-зона вроде Europe/Moscow. Сервер не проверяет реальную календарную дату: 31 февраля может пройти Pydantic-валидацию и упасть позднее внутри расчёта.

UI обязан хранить рядом с результатом полный снимок входа:

| Поле | Требование |
|---|---|
| Дата | ISO-дата YYYY-MM-DD после проверки календаря на клиенте |
| Время | HH:MM:SS, локальное для места рождения |
| Место | название, широта, долгота |
| Часовой пояс | числовой UTC-сдвиг, использованный в запросе |
| Аянamsha | одно из значений enum, по умолчанию LAHIRI |
| Версия расчёта | имя MCP, версия PyJHora и timestamp вызова |

Для контрольного пользователя передавать:

    place.name = Moscow, RU
    place.latitude = 55.7558
    place.longitude = 37.6173
    place.timezone = 4.0
    date_time.year = 2006
    date_time.month = 10
    date_time.day = 16
    date_time.hour = 13
    date_time.minute = 30
    date_time.second = 0
    ayanamsa = LAHIRI

Внутренние функции переводят дату в Julian Day и место в namedtuple Place. Они не получают отдельное поле IANA timezone. Поэтому UI не должен молча пересчитывать или заменять UTC-сдвиг после ответа MCP. Любое изменение timezone создаёт новый расчёт и новый cache key. Для этой даты изменение с 4.0 на 3.0 уже меняло Lagna с Scorpio на Sagittarius.

Поддерживаемые значения AyanamsaMode: LAHIRI, TRUE_PUSHYA, KP, RAMAN, YUKTESHWAR, JN_BHASIN, BABYL_KUGLER1, BABYL_KUGLER2, BABYL_KUGLER3. В интерфейсе по умолчанию выбран LAHIRI, а смена аянамши запускает полный пересчёт и очищает старые результаты вкладок.

Ошибки внутри полей имеют единую форму `{code, type, message, recoverable}`; внешние имена `error`, `planets_error` и `*_error` сохраняются для обратной совместимости.

## 5. Каноническая South Indian D1

### 5.1 Геометрия

Сетка представляет собой квадрат 4×4 с четырьмя угловыми и боковыми областями. Знаки стоят неподвижно, а не вращаются вокруг Lagna. Центральные четыре ячейки образуют внутреннее пустое поле.

| Координата | Знак | rasi_index |
|---|---|---:|
| row 1, col 1 | Aries | 0 |
| row 1, col 2 | Taurus | 1 |
| row 1, col 3 | Gemini | 2 |
| row 1, col 4 | Cancer | 3 |
| row 2, col 1 | Pisces | 11 |
| row 2, col 4 | Leo | 4 |
| row 3, col 1 | Aquarius | 10 |
| row 3, col 4 | Virgo | 5 |
| row 4, col 1 | Capricorn | 9 |
| row 4, col 2 | Sagittarius | 8 |
| row 4, col 3 | Scorpio | 7 |
| row 4, col 4 | Libra | 6 |

Внутренние row 2–3, col 2–3 остаются свободными для названия карты, легенды или режима отображения. В них нельзя помещать отдельные знаки или планеты.

Порядок знаков и словарь rasi_index должны жить в одном frontend-модуле. Нельзя вычислять координаты по названию знака, потому что MCP стабильно возвращает числовой индекс, а локализация названий может измениться.

### 5.2 Что выводится в ячейке

Каждая ячейка показывает короткое название знака, полный знак по hover или раскрытию, затем объекты, чей rasi_index равен индексу этой ячейки. Для D1 отображаются Sun, Moon, Mars, Mercury, Jupiter, Venus, Saturn, Rahu, Ketu, Uranus, Neptune и Pluto, поскольку текущий get_rasi_chart реально возвращает 12 записей. В пользовательском режиме outer planets можно свернуть, но их нельзя терять из raw snapshot.

Для каждой планеты в ячейке нужны:

- короткий идентификатор планеты;
- градусы внутри знака, округлённые до двух знаков;
- Nakshatra и Pada;
- индикатор ретроградности только при наличии достоверного поля в ответе;
- раскрытие строки с total_longitude и исходным JSON.

Сервер не возвращает готовую геометрию ячейки, координаты планеты, номер дома или South Indian layout. Эти поля строит frontend-адаптер. При нескольких объектах в одной ячейке используется вертикальный stack с переносом строк, а не наложение текста.

### 5.3 Lagna и дома

Lagna берётся из ascendant.rasi_index результата get_rasi_chart и выделяется отдельной рамкой или маркером L. Нельзя заменять его значением из get_planet_positions, пока не устранено расхождение источников.

Rasi D1 и Bhava chart должны визуально разделяться. Rasi показывает знак и состав планет по rasi_index. get_bhava_chart возвращает отдельные 12 bhavas с методом, средней точкой знака и occupants. Если UI выводит номер дома в квадрате, рядом должна быть подпись источника: whole-sign производное правило или конкретный ответ get_bhava_chart.

Для whole-sign производного номера дома допустима формула:

    house = ((rasi_index - ascendant_rasi_index) % 12) + 1

Формулу можно применять только при явной маркировке whole-sign. Если выбран method get_bhava_chart, номера и occupants берутся из ответа метода, а не пересчитываются поверх D1.

## 6. Вкладка 1: Карта и расчётные данные

Вкладка называется Карта. Она открывается после завершения базового расчёта и показывает South Indian D1 в верхней части. Пользователь сразу видит дату, место, timezone, ayanamsa, статус данных и кнопку раскрытия источника расчёта.

### 6.1 Первый экран

На первом экране должны быть:

1. квадрат D1 с фиксированными знаками;
2. компактная таблица планет с rasi, градусами, Nakshatra и Pada;
3. панель выбора варги с закрытым списком D1, D2, D3, D4, D7, D9, D10, D12, D16, D20, D24, D27, D30, D40, D45, D60.

Вызов get_divisional_chart по умолчанию не должен перегружать первый экран. D1 приходит из get_rasi_chart, остальные варги загружаются по запросу и кэшируются по ключу birth snapshot + divisor + ayanamsa. Для D1 нужно сохранять исходный ответ именно get_rasi_chart, а не повторно вызывать divisor=1.

### 6.2 Секции внутри вкладки

После карты идут раскрываемые блоки в следующем порядке:

- Panchanga: Tithi, Nakshatra, Yoga, Karana, Vaara, Masa, Samvatsara, Ritu;
- суточные времена: sunrise/sunset и moonrise/moonset;
- Rahu Kala и другие интервалы;
- Bhava chart;
- специальные Lagna;
- Ashtakavarga;
- Shadbala, Bhava Bala и Vimsopaka Bala;
- список фестивалей.

Каждая секция показывает tool name, время получения, статус и кнопку повторного вызова. Секция может быть открыта даже при ошибке другой секции. Один сбой samvatsara не должен скрывать D1.

### 6.3 Panchanga и время

Ответы времени приходят строками, а не типизированными датами. В контрольном ответе обнаружены отрицательное значение -20:33:38, значение больше суток 35:41:11, периоды 24:48:04 и 25:43:18, а также суточная отметка 00:33:45 (+1). UI не должен обрезать такие значения до 00:00 или молча приводить их по модулю 24. Нужен форматтер статуса:

| Значение | Отображение |
|---|---|
| HH:MM:SS от 00:00 до 23:59 | локальное время |
| значение больше 24 часов | время следующего дня с бейджем +1 день |
| отрицательное значение | Исходное значение и предупреждение MCP |
| N/A или отсутствующее поле | Нет данных |
| объект с error | Ошибка расчёта с раскрываемым текстом |

Karana в контрольном вызове пришёл с index 50 и именем Karana-50, потому что текущая карта имён converters.py не покрывает это значение. UI сохраняет исходное значение и не подменяет его самостоятельно.

### 6.4 Варги D2–D60

Enum DivisionalChart перечисляет D1, D2, D3, D4, D7, D9, D10, D12, D16, D20, D24, D27, D30, D40, D45 и D60. Сам tool принимает int без строгой валидации. Поэтому frontend использует закрытый enum-список и не даёт пользователю вводить произвольный divisor.

Ответ Dn содержит chart_type, divisor, ayanamsa, ascendant и planets. Текущая обёртка вычисляет ascendant варги формулой через D1 total_longitude × divisor % 360, тогда как планеты получает через charts.divisional_chart. Этот источник должен быть показан в diagnostics, а изменение логики асцендента требует отдельной проверки MCP.

### 6.5 Bhava, Ashtakavarga и сила

get_bhava_chart по умолчанию использует method=1, который в docstring описан как Equal House. Доступны методы 1–8: Equal House, KP, Sripathi, Placidus, Koch, Porphyrius, Regiomontanus, Campanus. В UI метод выбирается явно в отдельном control, а ответ сохраняется с method.

get_ashtakavarga возвращает bhinnashtakavarga по планетам и samudaya_ashtakavarga по 12 домам. Таблица должна иметь фиксированные строки планет и фиксированные столбцы 1–12, подсветку значения и раскрытие исходного ключа House N (Sign).

get_shadbala возвращает Sun–Saturn без Rahu и Ketu. Показываются компоненты sthana_bala, kala_bala, dig_bala, cheshta_bala, naisargika_bala, drik_bala, total_shastiamsas, total_rupas, strength_ratio, minimum_required и sufficient. get_bhava_bala показывает 12 домов. get_vimsopaka_bala показывает четыре группы Dasa Varga, Shad Varga, Sapta Varga и Shodasa Varga. Эти результаты нельзя объединять в один безымянный показатель силы.

## 7. Вкладка 2: Объяснение

Вкладка называется Объяснение. MCP возвращает расчётные признаки, но отдельного tool, который создаёт текстовое объяснение натальной карты, в текущем контракте нет. Поэтому вкладка строится поверх полученных результатов в application layer: она объясняет поля MCP и связывает их между собой, но не должна выдавать фразу как прямой ответ сервера.

Каждый блок имеет заголовок, короткое объяснение, источник, состояние уверенности и раскрытие деталей. Кнопка Подробнее открывает условие, затронутые планеты или дома, исходные значения и список tools, на которых основан блок.

### 7.1 Структура

| Блок | Источники MCP | Что объясняется |
|---|---|---|
| Основа карты | get_rasi_chart, get_bhava_chart | Lagna, знак, планета, дом, Nakshatra, Pada |
| Panchanga | get_panchanga | Tithi, Nakshatra, Yoga, Karana и календарные поля |
| Периоды | четыре dasha tools | текущий и ближайшие периоды, вложенность, границы |
| Йоги и доши | get_yogas, get_doshas, get_raja_yogas | condition, effect, present, details |
| Сила | get_shadbala, get_bhava_bala, get_vimsopaka_bala | значение, единица, threshold, достаточность |
| Временные расчёты | sunrise, rahu, muhurtha, festivals | локальные интервалы и их исходный статус |

### 7.2 Йоги и доши

get_yogas возвращает массив с id, chart, name, condition, effect или details, count и total_checked. Карточка должна показывать найдено/не найдено, название, условие и эффект. get_raja_yogas возвращает id и details, поэтому интерфейс не должен обещать структурированную категорию, которой нет в JSON.

get_doshas содержит description, который в текущем ответе может включать HTML-подобные теги вроде <html>. UI обязан прогонять текст через безопасный sanitizer и не вставлять исходную строку в DOM как доверенный HTML. Если sanitizer не поддержан, выводить plain text.

Поле present не может быть единственным основанием для критичного вывода: текущий код определяет часть статусов через поиск фразы there is no в описании. В карточке показывать description как первичный текст расчёта и отдельно отображать вычисленный boolean.

### 7.3 Dashas

По умолчанию загружать Vimsottari с include_antara=true и include_pratyantara=false. Первый уровень показывать как временную шкалу или таблицу maha_dashas. Подпериоды раскрываются по клику. Pratyantara доступен только после включения antara.

Yogini имеет цикл 36 лет, Vimsottari 120 лет, Ashtottari 108 лет. Ashtottari условна, но текущий tool не возвращает поле applicability. UI обязан различать техническую ошибку, отсутствие результата и состояние не применимо; для этого backend-адаптеру нужен диагностический статус, а не интерпретация пустого списка.

Narayana содержит divisional_chart и владык в названиях знаков. В selector явно показывать, для какой варги получена шкала.

### 7.4 Совместимость

get_compatibility не входит в основной экран одной натальной карты. Его можно использовать в отдельном режиме страницы после добавления второй анкеты. Текущий ответ содержит Ashta Koota с восемью полями и четыре south_indian_porutham: mahendra, vedha, rajju, sthree_dheerga. Он не возвращает отдельный South Indian score из десяти пунктов, поэтому UI не должен рисовать несуществующий общий балл.

Аянamsha берётся из данных мужчины. Если приложение позволяет менять её отдельно для двух анкет, до вызова нужно синхронизировать значения или показать явное предупреждение.

## 8. Вкладка 3: Вопросы к себе

Вкладка называется Вопросы к себе. В текущем MCP нет отдельного свободного question или interpretation tool. Вкладка требует клиентского оркестратора, который берёт результаты уже вызванных tools, определяет релевантные поля и формирует вопрос или объяснение на основании сохранённого snapshot.

Вопрос не должен запускать новый произвольный расчёт без отображения, какие факты использованы. В карточке вопроса должны быть текст, дата создания, используемые источники, раскрываемые факты и состояние ответа. Ответ может ссылаться только на поля, реально присутствующие в snapshot; если нужного расчёта нет, карточка предлагает загрузить соответствующий tool.

Минимальные группы вопросов:

- Как проявляется Lagna и какие планеты находятся в том же знаке? Источник: get_rasi_chart и при необходимости get_bhava_chart.
- Какие периоды сейчас активны и какие подпериоды следует посмотреть? Источник: get_vimsottari_dasha, затем выбранная альтернативная dasha.
- Какие комбинации, доши или показатели силы требуют подробного чтения? Источник: get_yogas, get_doshas, get_raja_yogas и strength tools.

Для каждого вопроса нужен режим Источники, где отображаются tool name, timestamp, параметры birth snapshot, divisor или method и сырой ответ. MCP сам не возвращает человеческие выводы и не поддерживает диалоговую историю, поэтому хранение истории вопросов относится к веб-сервису.

### 8.1 Демонстрационный блок второго экрана лендинга

Этот раздел описывает работающий фронтенд-пример, который пользователь видит во втором блоке посадочной страницы после формы расчёта. Он должен выглядеть как готовое окно продукта, но до подключения backend использует fixture-данные, локальное состояние вкладок и заглушки загрузки. В демонстрации запрещены реальные вызовы MCP, задержки сети и технические сообщения о незапущенном сервере.

Композиция строится как широкая тёмная сцена с космическим фоном, полупрозрачной чёрной панелью и медным акцентом. Слева находится вертикальный сайдбар, справа рабочая область выбранного раздела. В шапке рабочей области показываются имя профиля, дата и место рождения; кнопка `Скачать PDF` отделена от навигации и визуально не выглядит четвёртой вкладкой. На узком экране сайдбар превращается в горизонтальную навигацию сверху, а содержимое перестраивается в один столбец.

Сайдбар содержит ровно три кнопки с названиями `Натальная карта`, `Объяснение`, `Вопросы к себе`. Активная кнопка получает медную вертикальную линию, лёгкую заливку и состояние `aria-selected=true`. Клик меняет панель без перезагрузки; клавиши стрелок переключают вкладки по кругу, `Home` и `End` переходят к началу и концу. Каждая кнопка связана с `tabpanel` через `aria-controls`, а заголовок панели остаётся доступным скринридеру. В текущем макете это уже реализовано в `ResultsShowcase`, включая вложенный набор вкладок `Планеты`, `Дома`, `Аспекты` внутри карты.

Вкладка `Натальная карта` должна показывать заголовок, строку `дата · время · город`, кнопку редактирования входа и квадратную South Indian D1. Сетка 4×4 держит фиксированные знаки, не вращается вокруг Lagna и не превращается в западный круг или северную ромбовидную схему. В центральной области размещаются название карты и краткая сводка. Справа или ниже идут вложенные панели `Планеты`, `Дома`, `Аспекты`, затем карточка ключевых аспектов. Данные примера должны быть визуально правдоподобными, но маркироваться как демонстрационные до подключения расчёта.

В ячейке D1 знак читается первым, затем вертикально перечисляются объекты с коротким идентификатором, градусами, Nakshatra и Pada. При наведении или нажатии появляется компактный popover с полным названием, `total_longitude`, источником и состоянием ретроградности. Переполнение ячейки решается стеком и внутренним скроллом; текст не накладывается. Увеличение карты, сброс масштаба и раскрытие источника проектируются как отдельные ghost-кнопки и в демо могут быть placeholder-кнопками с понятным `aria-label`.

Вкладка `Объяснение` начинается с короткого тезиса о карте, затем показывает секции `Основы карты`, `Планеты в карте` и `Дополнительные элементы`. Карточка содержит символ, название, одну-две строки смысла и явную кнопку `Подробнее`; нажатие раскрывает детали внутри карточки или в боковом drawer. В раскрытии видны затронутые планеты или дома, исходные значения, название источника и ссылка `Вернуться к карте`. Для демо раскрытие работает локально, а блок источников показывает placeholder со структурой будущего ответа.

Вкладка `Вопросы к себе` показывает сетку промпт-карточек с вопросом и основанием из карты. В верхней части находятся фильтры-темы `Отношения`, `Работа`, `Деньги`, `Энергия`, `Смысл` и кнопка `Задать свой вопрос`. Нажатие на карточку открывает состояние выбранного вопроса: текст вопроса, placeholder ответа, кнопку раскрытия фактов и ссылку `Новый вопрос`. В демо ответ заменяется skeleton или коротким placeholder; интерфейс заранее резервирует место под источники и состояние `Недостаточно данных`, чтобы позже подключить application layer без изменения композиции.

Для ширины от 900 px сайдбар остаётся слева, карта и таблицы располагаются в рабочей области. Ниже 900 px навигация переходит наверх и становится горизонтально прокручиваемой без обрезания подписей. Ниже 620 px карточки, таблицы и сетка переходят в один столбец; горизонтальный скролл разрешён только внутри широкой таблицы данных, но не у всей страницы. При `prefers-reduced-motion: reduce` смена вкладки происходит без смещения и затухания.

Демо проверяется по трём сценариям: открыть каждую боковую вкладку кликом, переключить её с клавиатуры, раскрыть вложенную секцию или карточку. Для каждого сценария нужны состояния `loading`, `success`, `partial`, `empty` и `error`; placeholder не должен маскировать ошибку или ломать высоту соседних блоков. После подключения backend меняется источник fixture-данных, а названия вкладок, порядок блоков, South Indian геометрия, точки нажатия и состояния загрузки сохраняются.

## 9. Единый адаптер данных

Frontend или backend-for-frontend должен преобразовывать разрозненные ответы MCP в единый объект ChartSnapshot:

    ChartSnapshot
      input
      provenance
      d1
      divisionalCharts
      panchanga
      bhava
      lagnas
      dashas
      yogas
      doshas
      strengths
      timeWindows
      festivals
      diagnostics

Для каждой секции хранить status: success, partial, error, empty, unavailable. Не использовать только наличие корневого error: текущий MCP смешивает корневой error, field.error, *_error, N/A, пропущенные ключи и пустые массивы.

Адаптер обязан:

1. проверять обязательные поля секции;
2. сохранять raw JSON без преобразования;
3. нормализовать числа, не теряя исходное значение;
4. сохранять tool name, параметры и timestamp;
5. различать технический сбой, отсутствие события и не применимый расчёт;
6. выдавать UI-модель для South Indian grid независимо от локализации текста.

Cache key строится из нормализованного birth snapshot, ayanamsa, имени tool и параметров divisor, method, include_antara, include_pratyantara. Нельзя кэшировать только по дате: изменение координат, timezone или аянамши меняет карту.

## 10. Состояния интерфейса

| Состояние | Условие | UI |
|---|---|---|
| Loading | tool вызван, ответа нет | skeleton соответствующей секции, без пустых нулей |
| Success | обязательные поля есть, ошибки отсутствуют | обычный блок |
| Partial | часть полей есть, рядом error или *_error | успешные поля видимы, проблемное поле помечено |
| Empty | пустой массив, N/A или отсутствующее необязательное поле | Нет данных с причиной, если она известна |
| Unavailable | система условна или tool не поддержал результат | Не применимо, без красного сообщения о сбое |
| Error | протокольная ошибка, валидация или корневой error | повторить, показать техническую деталь в diagnostics |

Ошибка одной функции не должна блокировать остальные независимые функции. На первом экране критичны D1 и input snapshot; Panchanga, dashas и strength могут догружаться параллельно.

## 11. Статус P0-исправлений MCP

Первые четыре P0 закрыты в текущем working tree активного checkout и закреплены регрессионными тестами. `get_planet_positions` теперь получает положения через `charts.rasi_chart`, поэтому его классические позиции совпадают с каноническим D1 на одном входе. `ensure_ephemeris_path()` выбирает каталог PyJHora, проверяет каталог и `seplm48.se1`, затем явно вызывает `swe.set_ephe_path()` до расчёта; `samvatsara` в свежем процессе возвращается без ошибки.

Все инструменты используют общий `error_payload()` с полями `code`, `type`, `message`, `recoverable`. Частичная ошибка сохраняется в исходном месте ответа, поэтому UI может показать успешные поля и отдельный diagnostic badge. Все 22 зарегистрированных tools получили именованные `TypedDict`-аннотации из `schemas.py`; FastMCP публикует детальные output schemas вместо безымянного `object`.

Пятый пункт остаётся ограничением входного контракта: MCP принимает числовой UTC-сдвиг, но не принимает IANA-зону и не заменяет клиентскую календарную проверку. UI обязан валидировать календарную дату, сохранять введённый локальный timestamp и показывать рядом с результатом фактический numeric timezone.

## 12. P1-дефекты и ограничения

- get_special_lagnas обещает Bhava Lagna в docstring, но возвращает только hora, ghati, vighati, pranapada, indu и sree lagna;
- get_divisional_chart принимает произвольный int, хотя enum ограничивает список варг;
- ascendant в divisional chart вычисляется обёрткой, а не тем же источником, что планеты;
- get_bhava_chart принимает произвольный method без схемы 1–8;
- Ashtottari не возвращает applicability;
- get_compatibility использует только ayanamsa мужчины и возвращает четыре porutham вместо заявленного полного набора;
- outer planets приходят из get_rasi_chart, но не входят в get_planet_positions и Shadbala;
- format_time допускает отрицательные и сверхсуточные строки;
- tools сохраняют частичные результаты, а единый error_payload используется для вложенных ошибок; safe_call остаётся вспомогательным API для простых обёрток;
- HTTP, stdio, Bearer-аутентификация и Docker не имеют отдельного интеграционного теста; текущие тесты в основном вызывают Python-функции напрямую.

## 13. Приёмочные тесты UI

### 13.1 D1 и South Indian grid

- При контрольном snapshot Lagna отображается в Scorpio.
- Ровно 12 planet entries из get_rasi_chart распределяются по rasi_index.
- Cancer содержит Moon и Saturn; Virgo содержит Sun, Venus и Ketu; Libra содержит Mars, Mercury и Jupiter; Pisces содержит Rahu.
- Центральные четыре ячейки не используются как знаки.
- Смена ayanamsa или timezone полностью обновляет D1 и provenance.
- Смешивание данных get_planet_positions с сеткой невозможно на уровне адаптера.

### 13.2 Варги и дома

- Selector предлагает только enum-варги.
- Двойной клик или повторное открытие D9 использует cache key и не меняет D1.
- Выбранный method Bhava виден рядом с результатом.
- Номер дома имеет badge whole-sign или bhava method, а не выглядит как безымянная часть знака.

### 13.3 Ошибки и Panchanga

- Ошибка samvatsara оставляет D1 и остальные Panchanga-поля доступными.
- -20:33:38, 35:41:11 и 24:48:04 отображаются как исходные аномальные значения с предупреждением.
- HTML-подобный description досхи не исполняется.
- Корневой error и вложенный field.error дают разные визуальные состояния.

### 13.4 Dashas, explanation, questions

- Уровни maha dasha, antara и pratyantara раскрываются независимо и сохраняют границы start/end.
- Не применимая Ashtottari не показывается как технический crash.
- Карточка объяснения показывает исходный tool и факты.
- Вкладка вопросов сообщает, каких данных не хватает, и не притворяется встроенным MCP-инструментом.
