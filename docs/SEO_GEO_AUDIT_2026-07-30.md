## 1. Вердикт

VedicWay пока нельзя выводить в поисковое продвижение. На 30 июля 2026 года домен показывает системную заглушку Timeweb, HTTP не переводит посетителя на HTTPS, сертификат выпущен на `*.timeweb.ru`, а защищённое соединение с `vedicway.ru` завершается ошибкой несоответствия имени. Главная страница заглушки отвечает кодом 200, `/guide`, `/blog`, `/robots.txt` и `/sitemap.xml` отвечают 404. Поисковый робот видит чужой хостинговый экран вместо сервиса. Любая работа над заголовками, статьями или ссылками начнёт приносить результат только после исправления этого блока.

Кодовая база содержит сильную техническую заготовку: статический пререндер ключевых страниц, серверные HTML-версии статей, настоящие 404 в конфигурации Nginx, канонические URL, динамический Sitemap, семантическую разметку и массив из 202 подготовленных материалов. Сборка проходит, 57 фронтенд-тестов и 8 целевых серверных тестов зелёные. Однако пользовательский JavaScript заменяет серверную разметку через `createRoot`, повторно запрашивает тот же контент из API и при сбое способен стереть индексируемую статью, выставив `noindex`. Метаданные и JSON-LD до выполнения JavaScript и после него расходятся.

Контентный массив нельзя публиковать одним пакетом. Две статьи содержат нечитаемый текст после двойной перекодировки, 184 статьи ведут на несуществующий маршрут `/chart`, в 61 материале повторяются предложения внутри одного документа, а 28 длинных шаблонных фраз встречаются минимум в пяти статьях. Внешние источники собраны достаточно широко, но читатель их не видит: в HTML статей нет кликабельных внешних ссылок, хотя в служебных файлах найдено 493 внешних источника. Такая конструкция ослабляет доверие, цитируемость и пригодность текста для генеративных ответов.

Публичной сущности VedicWay в поиске почти нет. Запрос `site:vedicway.ru` в Яндексе дал 0 результатов, домен не подключён к доступному аккаунту Яндекс Вебмастера, а счётчик Метрики для проекта не найден. Точное название конкурирует с давно существующим `vedicway.com` и другими проектами Vedic Way. Генеративная система не получает устойчивого набора независимых источников, по которым можно отличить российский калькулятор от одноимённых организаций.

## 2. Рамка аудита и доказательность

Контекст задачи: репозиторий содержит рабочий калькулятор, платный персональный разбор, правовые страницы и большую библиотеку по джйотишу. Цель SEO состоит в получении релевантного трафика на расчёт и статьи. Цель GEO состоит в том, чтобы поисковые и генеративные системы могли найти страницу, извлечь точный фрагмент, проверить автора и сослаться на VedicWay.

Успех измеряется четырьмя результатами: домен стабильно индексируется; коммерческие запросы приводят на калькулятор; информационные запросы распределены по непересекающимся материалам; VedicWay появляется в источниках генеративных ответов по джйотишу. В аудит вошли production-домен, фронтенд, серверный SEO-рендер, маршрутизация Nginx, 202 подготовленные статьи, схема публикации, поисковый спрос, текущая выдача и публичные признаки сущности. Персональные страницы карт, платёжный процесс и трактовки проверялись лишь там, где они влияют на обход, индексирование и доверие.

Решения принимают владелец продукта и редактор. Platform-разработчик отвечает за DNS, TLS и Nginx; frontend-разработчик - за рендер и скорость; backend-разработчик - за публикацию и Sitemap; редакция - за качество, источники и авторство. SEO-специалист ведёт семантику, поисковые панели и эксперименты. Юрист подтверждает формулировки о персональных данных, оплате и границах астрологического сервиса.

В отчёте используются следующие метки:

| Метка | Значение |
|---|---|
| **Измерено** | Результат команды, HTTP-запроса, браузерного теста, Lighthouse, поискового запроса или подсчёта файлов |
| **Рассчитано** | Значение выведено из измеренных данных по указанному правилу |
| **Данные репозитория** | Факт читается из кода, конфигурации, теста или контентного файла |
| **Оценка** | Профессиональное решение, которое надо подтвердить после запуска |
| **Прокси** | Косвенный публичный сигнал при отсутствии закрытых данных |

Формальный балл CORE-EEAT не рассчитан. Методика плагина требует полного набора доказательств, исполнения штатного скорера и данных по применимым пунктам. Search Console, рабочий Яндекс Вебмастер, редакционные подтверждения, юридические согласования и полевые данные отсутствуют. Подмена неизвестных величин нулями исказила бы результат. По той же причине не рассчитан CITE: нет зафиксированной группы сопоставимых доменов, экспорта ссылок, ручных санкций и проверенного размера рынка. В отчёте дана качественная диагностика каждого слоя, а Lighthouse оставлен отдельным лабораторным измерением.

## 5. Production: индексирование сейчас заблокировано

### 5.1 DNS, TLS и HTTP

**Измерено 30 июля 2026 года:** `vedicway.ru` разрешается в `92.53.96.169`. Сервер предъявляет сертификат `CN=*.timeweb.ru`, выпущенный GlobalSign и действующий с 17 июня 2026 года до 2 января 2027 года. Имя `vedicway.ru` в него не входит. Проверяемый HTTPS-клиент возвращает `SEC_E_WRONG_PRINCIPAL`.

HTTP и принудительный HTTPS с отключённой проверкой сертификата возвращают страницу Timeweb с title `Ваш аккаунт готов к работе!`, статусом 200 и размером 38 873 байта. HTTP не перенаправляется на HTTPS. Пути `/guide`, `/blog`, `/robots.txt` и `/sitemap.xml` возвращают 404. Это классический случай, когда поисковик может закрепить за доменом чужой шаблон, а настоящий сайт остаётся вне обхода.

**P0-действие:** связать домен с production ingress, выпустить сертификат на `vedicway.ru` и при необходимости `www.vedicway.ru`, выбрать одну основную версию, а вторую переводить 308-редиректом. HTTP должен всегда отвечать 308 на тот же путь в HTTPS. До завершения переключения нельзя отправлять Sitemap и покупать ссылки на домен.

Критерии приёмки:

```bash
curl -I http://vedicway.ru/
# 308 Location: https://vedicway.ru/

curl -I https://vedicway.ru/
# 200, корректный сертификат, title и body VedicWay

curl -I https://vedicway.ru/robots.txt
curl -I https://vedicway.ru/sitemap.xml
# 200 и правильный Content-Type

curl -I https://vedicway.ru/url-kotorogo-net
# 404
```

**Измерено:** `site:vedicway.ru` в Яндексе дал 0 результатов. Среди доступных хостов Яндекс Вебмастера есть только другой проект, `vedicway.ru` отсутствует. Среди доступных счётчиков Метрики нет VedicWay; внутренний SEO-контракт репозитория содержит `counter_id: 0`. Точный запрос домена показывает преимущественно агрегаторы доменов `rankw.ru` и `all-domains.pro`.

Для Яндекса отдельно следует проверить режим JavaScript-рендера. ## 6. Технический SEO-аудит репозитория

### 6.1 Сильные стороны реализации

Сборка `package.json:8` запускает TypeScript, Vite и `scripts/prerender-seo.mjs`. Пререндер создаёт отдельные HTML-файлы для главной, хабов, правовых и noindex-страниц, прописывает canonical, robots, Open Graph и JSON-LD. Серверный модуль `backend/src/vedicway_backend/content_api.py` отдаёт полноценные HTML-страницы статей и хабов. Nginx переводит конечный слеш кодом 308, для неизвестных URL возвращает 404, закрывает API и персональные карты заголовком `X-Robots-Tag`, а Sitemap получает из backend с запасным статическим файлом.

URL статей состоят из строчных ASCII-символов и дефисов. Канонические адреса абсолютные. Персональные `/chart/{id}` исключены из индекса, что соответствует чувствительности данных. `lang="ru"` и `inLanguage: "ru-RU"` согласованы. Hreflang не нужен, пока у сервиса существует одна русская версия.

### 6.2 Серверный HTML уничтожается клиентским рендером

`src/main.tsx:23` вызывает `createRoot` для контейнера, куда пререндер или backend уже положил содержимое. React заменяет этот DOM. Хаб снова вызывает публичный API, статья в `src/components/ArticlePage.tsx:138-162` снова запрашивает материал и комментарии. При ошибке статья превращается в состояние `Материал не найден`, а `src/components/ArticlePage.tsx:164-172` добавляет `noindex`.

Эта схема даёт поисковому роботу два документа по одному URL. Робот без JavaScript получает серверный текст. Робот с рендером получает результат повторного API-запроса. Краткий сбой backend на второй стадии способен удалить основной текст и передать `noindex`, хотя первый HTTP-ответ был полноценным. Google официально описывает последовательность crawl, render, index и рекомендует проверять именно отрендеренный HTML. Яндекс сам решает, выполнять ли JavaScript, поэтому две системы могут зафиксировать разные версии страницы.

Локальный браузерный тест подтвердил поведение: при недоступном API `/guide` показал 0 материалов, `/blog` вывел `Библиотека временно недоступна`, а правовая страница заменила пререндер сообщением `Документ временно недоступен`. В логе браузера появился 502 для `/api/v1/legal/config`. Исходный HTML legal содержит только заголовок и обещание загрузить полный документ после старта приложения, поэтому при сбое пользователь и выполняющий JavaScript робот не получают правовой текст.

**P0-решение:** выбрать один согласованный способ.

1. Сервер формирует тот же React-деревом HTML, клиент запускает `hydrateRoot`, а данные статьи передаются в безопасном bootstrap JSON без повторного обязательного запроса.
2. Серверная статья остаётся постоянным семантическим DOM, React монтирует комментарии, фильтры и анимации в отдельные островки. Сбой API не меняет title, robots и основной текст.

Для текущего проекта второй путь потребует меньше риска. Главный критерий: основной текст, H1, canonical и JSON-LD не зависят от клиентского запроса после первого ответа.

### 6.3 Метаданные расходятся до и после JavaScript

`index.html:28` и `scripts/prerender-seo.mjs:46` задают title `Натальная карта онлайн с персональным разбором | VedicWay`. Клиент в `src/App.tsx:61-70` меняет его на `Ведическая натальная карта онлайн | VedicWay` и сокращает description. Пререндер главной создаёт `WebSite` и `FAQPage`, а `src/lib/seo.ts:48-58` удаляет серверные скрипты с `data-vedicway-seo-schema` и добавляет только клиентский `WebSite`.

Title, description, JSON-LD и видимый текст должны собираться из одного типизированного объекта. Пререндер, backend и клиент обязаны импортировать одну конфигурацию либо получать один payload. Интеграционный тест должен сравнивать исходный HTML и DOM после загрузки по полям `title`, `description`, `canonical`, `robots`, H1 и нормализованному JSON-LD.

### 6.4 Robots и noindex конфликтуют

`public/robots.txt` запрещает `/access/recovery` и `/privacy/request`, а Nginx одновременно передаёт для них `X-Robots-Tag: noindex`. Яндекс прямо указывает: запрещённую в `robots.txt` страницу робот может показать в поиске по внешним сигналам, при этом он не увидит `noindex`. Recovery, confirm и privacy request лучше разрешить для обхода и оставить `noindex, nofollow, noarchive` в HTTP и HTML. Персональные `/chart/{id}` должны оставаться закрытыми, но настоящую приватность обеспечивает авторизация, а файл robots лишь экономит обход.

Текущий общий `User-agent: *` разрешает обход AI-краулерам. Это приемлемый режим для максимальной поисковой и GEO-видимости, но политика не разделяет поисковое извлечение и обучение моделей. Раздельное решение дано в разделе 13.

### 6.5 Sitemap и публикационная база

Локальная `.data/content.sqlite3` содержит 0 статей и 0 медиа. Каталоги `content/astrology-guide/articles` представляют подготовленный импорт, публикацией они не считаются. Динамический Sitemap добавляет только записи со статусом `published`; запасной `public/sitemap.xml` содержит `/`, `/guide` и `/blog`. При недоступном backend поисковик не увидит статьи.

Sitemap должен включать только канонические URL со статусом 200. Для статей нужен точный `lastmod` из редакционного обновления. Главная и хабы тоже должны получать `lastmod`, когда меняется их видимое содержимое. После импорта следует сверить четыре множества: опубликованные записи базы, URL Sitemap, канонические URL HTML и ответы 200. Разность любого множества блокирует релиз.

### 6.6 Дубли правовых маршрутов

Nginx отдельно отдаёт `/legal/offer` и `/legal/user-agreement`, а также `/legal/privacy` и `/legal/privacy-policy`. Пререндер назначает каждому варианту собственный canonical. После запуска JavaScript компонент LegalPage меняет canonical псевдонима на основной путь. Снова возникают две версии документа.

Оставить надо `/legal/offer` и `/legal/privacy`. Псевдонимы должны отвечать 308 на основной URL. То же правило следует закрепить тестом HTTP-контракта, чтобы старые внешние ссылки сохраняли вес.

### 6.7 Кэширование и сборка

Backend-страницы всегда подключают `/assets/seo-entry.js` и `/assets/seo-entry.css`. В измеренной сборке JavaScript занимает 479 824 байта без сжатия и около 152 KB gzip, CSS - 186 334 байта и 36,61 KB gzip. Файлы имеют стабильные имена, а Nginx в `docker/nginx/nginx.conf:226-233` задаёт им `expires -1`. Каждый переход к статье снова оплачивает передачу этих ресурсов.

Надёжное решение: брать хешированные имена из Vite manifest и вставлять их в серверный HTML. Тогда Nginx может отдавать `Cache-Control: public, max-age=31536000, immutable`. Если серверу нужен стабильный адрес, имя должно включать номер сборки, а HTML переключаться атомарно. Повторный запуск `node scripts/prerender-seo.mjs` в Dockerfile после `npm run build`, где этот скрипт уже выполняется, надо убрать.

### 6.8 Служебные детали

`site.webmanifest` содержит только иконку 320 на 320. Для установки приложения стоит добавить 192 и 512 пикселей, включая `maskable`; поисковое влияние минимально. Open Graph использует тяжёлый `hero-space-light.png` размером около 2,13 MB и не передаёт `og:image:alt`, ширину и высоту. Для социальных превью нужен отдельный файл около 1200 на 630 с весом до 300 KB. У каждой статьи уже есть WebP не меньше 1200 на 630, но Google рекомендует несколько высококачественных вариантов 1:1, 4:3 и 16:9 для Article.

Content Security Policy не разрешает произвольный inline JavaScript. JSON-LD имеет тип `application/ld+json`, поэтому его надо проверить в production через Google Rich Results Test, Schema Markup Validator и консоль браузера. Аудит не объявляет CSP-дефект без такого теста.

Маршруты статьи, хаба, legal и результата надо загружать через динамические импорты. GSAP, ScrollTrigger, комментарии и редакционные компоненты не должны входить в стартовый пакет калькулятора. Целевой начальный JavaScript для главной - до 100 KB gzip. Критический CSS первого экрана надо отделить от стилей длинных страниц.

Brand mark лучше перевести в компактный SVG либо WebP. Аватары можно собрать в лёгкий спрайт или удалить, если за ними нет проверяемых отзывов. Набор шрифтов надо сократить до используемых начертаний или двух variable-font файлов.

После production-запуска следует собирать реальные Web Vitals по типу страницы и устройству. Контроль выполняется на p75 мобильных просмотров: LCP до 2,5 секунды, INP до 200 миллисекунд, CLS до 0,1. Лабораторный Lighthouse запускается на каждом релизе, но решение о готовности принимает полевой ряд за 28 дней.

Lighthouse нашёл нарушения ARIA-ролей, родительских связей и цветового контраста. Они ухудшают работу интерфейса с клавиатурой и вспомогательными технологиями. Исправления входят в P1, хотя прямой коэффициент ранжирования из этих баллов выводить нельзя.

## 8. On-page аудит главной страницы

### 8.1 Поисковая роль

Главная должна владеть одним коммерческим кластером: `ведическая натальная карта онлайн`, `рассчитать натальную карту джйотиш`, `натальная карта онлайн с расшифровкой`. Создание отдельной страницы под каждый вариант приведёт к каннибализации. Общий запрос `натальная карта онлайн` шире продукта и смешивает западную астрологию, телевизионные названия и бесплатные калькуляторы. VedicWay может участвовать в нём, если первая экранная область сразу объясняет сидерический метод и состав результата.

Текущий H1 `ПОЗНАЙ СЕБЯ ЧЕРЕЗ КОСМОС` не называет услугу. Лид `Натальная карта раскрывает ваш уникальный рисунок судьбы. Узнайте своё предназначение и скрытые ресурсы` делает сильные обещания без объяснения метода. На первом экране не видно, какая часть бесплатна, когда возникает оплата и что пользователь получит до неё.

Рекомендуемый набор:

```text
Title:
Ведическая натальная карта онлайн: расчёт джйотиш | VedicWay

H1:
Рассчитайте ведическую натальную карту

Description:
Постройте сидерическую карту по дате, точному времени и месту рождения. Посмотрите положения грах, домов и лагны, затем получите персональный разбор VedicWay.
```

Если базовый расчёт действительно бесплатен, это слово следует добавить в title, description и видимый текст с точным ограничением: `Карта и основные положения бесплатно; полный персональный разбор оплачивается отдельно`. Если бесплатного результата нет, запросы со словом `бесплатно` нельзя обещать в сниппете.

### 8.2 Первый экран и доверие

Первый экран должен за 10 секунд отвечать на четыре вопроса: какие данные нужны, по какой системе идёт расчёт, что входит в результат и сколько стоит следующий шаг. Рядом с формой нужен короткий методологический блок: сидерический зодиак, используемая аянамша, система домов и источник эфемерид. Для пользователя с неизвестным временем рождения должен быть отдельный сценарий с честным описанием ограничений.

В `src/App.tsx:132-137` опубликованы `4.9 из 5` и `более 18 000 карт построено`. В репозитории нет методики, периода и источника этих чисел. Их надо удалить до проверки. Если данные подтверждены, рядом указываются количество оценок, период, платформа сбора и ссылка на правила расчёта рейтинга. Разметку `AggregateRating` добавлять нельзя, пока отзывы и оценка не доступны пользователю на странице и не проходят требования поисковой системы.

### 8.3 Содержательная структура главной

После формы нужны компактные блоки с самостоятельной поисковой ценностью: что показывает ведическая карта; как VedicWay считает положения; что пользователь увидит в бесплатной и платной части; пример результата; ограничения метода; автор и редакционная проверка. FAQ можно оставить для людей, но `FAQPage` больше не заслуживает отдельного SEO-приоритета: Google удалил показ FAQ rich results 7 мая 2026 года. Разметка не повышает позиции и не компенсирует слабый первый экран.

### 9.4 Риск шаблонного массива

Полных дублей статей по SHA не найдено, идентичны только два абзаца между разными документами. Главный риск создаёт повторяемый редакционный каркас. Самые перегруженные внутренними повторами материалы: `moon-based-and-lagna-based-dashas` - 30 повторных вхождений, `ogranicheniya-rascheta-natalnoj-karty` - 28, `polozheniya-grah-v-sidereicheskoj-karte` - 20, `yulianskiy-den` - 18, `koordinaty-mesta-rozhdeniya-v-karte` - 18.

Редакционный шлюз должен считать долю повторных предложений внутри документа и document frequency длинных предложений по всему корпусу. Материал блокируется, когда повтор не служит таблице, определению или обязательному предупреждению. Для каждой статьи редактор добавляет один собственный пример, один проверяемый расчёт либо таблицу и один тезис, которого нет в соседних документах.

### 9.5 Потенциальная каннибализация

Без показов и сравнения пересечения SERP нельзя объявлять каннибализацию доказанной. Названия уже показывают кластеры, которые надо проверить до публикации:

| Кластер | Страницы | Предварительное решение |
|---|---|---|
| Что изучает джйотиш | `chto-izuchaet-dzhyotish`, `chto-izuchaet-dzhyotisha` | Вероятный дубль: выбрать основную, вторую объединить и поставить 308 |
| Девять грах | `devyat-grah`, `navagraha-devyat-grah` | Развести базовое определение и подробную таблицу либо объединить |
| Достоинства планет | `ekzaltaciya-debilitaciya-sobstvennyy-znak`, `ekzaltaciya-i-debilitaciya-grah`, `svakshetra-mulatrikona-uchcha` | Назначить отдельные намерения и взаимную иерархию |
| Аянамша | `ayanamsha`, `ayanamsha-lahiri-raman-true-chitra` | Сохранить родительскую и сравнительную страницы |
| Два зодиака | Материалы о sidereal и tropical | Один обзор, остальные отвечают на узкие вопросы |

Решение принимается по трём признакам: совпадение целевых запросов, пересечение топ-10 минимум на 40 процентов и отсутствие самостоятельного пользовательского результата. При совпадении всех признаков страницы объединяются. При различии результата меняются title, H1, лид, внутренние анкоры и примеры.

### 9.6 Хаб на 202 карточки

Изолированный запуск серверного рендера с 202 опубликованными записями дал HTML 303 205 байт без сжатия и 45 240 байт gzip. Страница содержит 202 карточки, 203 изображения, 202 lazy-image и 404 вхождения ссылок на статьи, поскольку карточка и заголовок ведут на один URL. JSON-LD занимает 38 739 байт.

Хаб надо разделить на четыре индексируемые категории:

```text
/guide
/guide/osnovy-astrologii
/guide/planety-i-doma
/guide/vremya-i-cikly
/guide/praktika-chteniya
/guide/<slug>
```

Главный `/guide` описывает учебный путь и показывает лучшие материалы каждой темы. Категория отдаёт до 24 карточек и обычные HTML-ссылки на последующие страницы. Фильтры сложности и поиск не должны создавать индексируемые комбинации URL, пока под них нет отдельного спроса и редакционного текста. `/blog` следует оставить для датированных исследований, обновлений калькулятора и редакционных разборов; переносить туда вечнозелёные учебные статьи не надо.

## 10. Структурированные данные

### 10.1 Что реализовано

Пререндер главной создаёт `WebSite` и `FAQPage`. Хабы получают `CollectionPage` и `BreadcrumbList`, серверный хаб добавляет `ItemList`. Статья получает `Article` либо `BlogPosting`, `BreadcrumbList`, headline, description, image, даты, количество слов, раздел, ключевые слова, автора, издателя и citations из `schema_extra`. В целом типы выбраны разумно.

Проблема лежит в согласованности. После клиентского рендера главная теряет `FAQPage`, серверный и клиентский граф статьи собираются в разных местах, а author остаётся организацией с названием `Редакция VedicWay` без URL. В manifest только двух материалов заявлены `Article` и `FAQPage`, хотя backend выводит `Article` и `BreadcrumbList`. Декларативный контракт не описывает реальный результат.

### 10.2 Целевой граф

Для всего сайта нужен один стабильный объект организации:

```json
{
  "@type": "Organization",
  "@id": "https://vedicway.ru/#organization",
  "name": "VedicWay",
  "url": "https://vedicway.ru/",
  "logo": {
    "@type": "ImageObject",
    "@id": "https://vedicway.ru/#logo",
    "url": "https://vedicway.ru/assets/brand-mark.png"
  }
}
```

В `sameAs` разрешены только подтверждённые профили, которыми управляет владелец. Одноимённый `vedicway.com` нельзя указывать даже ради заполнения поля. Для автора предпочтителен `Person` с именем, биографией, редакционной ролью и URL профиля. Если материал подписывает редакция, объект `Organization` должен вести на страницу `/editorial-policy` либо `/about`, где названы ответственные люди и порядок проверки. Приглашённый эксперт или проверяющий указывается отдельным объектом лишь после реального участия.

Article должен ссылаться на общий publisher через `@id`, содержать `datePublished`, честный `dateModified`, `mainEntityOfPage`, `inLanguage`, `articleSection`, видимые citations и массив изображений в форматах 1:1, 4:3 и 16:9. BreadcrumbList сохраняется. Для хаба достаточно `CollectionPage`, `BreadcrumbList` и компактного `ItemList` текущей страницы пагинации.

`FAQPage` можно оставить как семантическое описание видимого FAQ, но Google прекратил поддержку соответствующего rich result 7 мая 2026 года. Product, Review и AggregateRating нельзя добавлять без реального предложения, цены и доступных пользователю отзывов. `WebApplication` допустим как семантический тип калькулятора, однако сам по себе не даёт гарантированного расширенного сниппета.

### 10.3 Контроль разметки

На каждой сборке надо извлекать JSON-LD из исходного HTML и из DOM после JavaScript, нормализовать порядок ключей и сравнивать смысловой граф. Затем 10 репрезентативных URL проверяются в Google Rich Results Test, Schema Markup Validator и валидаторе Яндекс Вебмастера. Поля structured data обязаны совпадать с видимым текстом; разметка не должна обещать рейтинг, бесплатность или дату, которых страница не показывает.

## 13. GEO: генеративные ответы и AI-поиск

### 13.1 Текущая готовность

GEO начинается с доступного поискового документа. Google сообщает, что для AI Overviews и AI Mode применяются обычные основы Search: Googlebot должен иметь доступ, текст должен присутствовать на странице, внутренние ссылки должны работать, а structured data - совпадать с видимым содержимым. Яндекс Нейро отбирает материалы из поиска, анализирует несколько источников и показывает ссылки. По данным официального блога Яндекса, шанс участия растёт у страниц, которые хорошо ранжируются и полезно отвечают на вопрос.

VedicWay сейчас не проходит первый фильтр: production отдаёт заглушку, индекс Яндекса пуст, содержательная сущность бренда не подтверждена. После деплоя второй фильтр тоже останется слабым: в статьях нет видимых внешних источников, автор не имеет профиля, а шаблонные абзацы затрудняют выбор уникального фрагмента.

### 13.2 Политика AI-краулеров

Поисковое извлечение и обучение модели требуют раздельного решения. Для максимальной цитируемости следует разрешить поисковые роботы. Обучающие роботы можно разрешить или закрыть по решению владельца; это не должно случайно блокировать AI-поиск.

| Платформа | User-agent | Назначение по официальной документации | Рекомендация |
|---|---|---|---|
| Google | `Googlebot` | Обычный поиск, AI Overviews и AI Mode | Разрешить публичный контент |
| Google | `Google-Extended` | Отдельное управление некоторыми сценариями обучения и grounding, не контроль AI Overviews | Принять отдельное бизнес-решение |
| Яндекс | `YandexBot` | Поиск | Разрешить публичный контент |
| Яндекс | `YandexAdditional` | Источники Нейро и быстрых ответов | Разрешить для GEO |
| OpenAI | `OAI-SearchBot` | Поиск ChatGPT | Разрешить публичный контент |
| OpenAI | `GPTBot` | Обучение генеративных моделей | Отдельное бизнес-решение |
| OpenAI | `ChatGPT-User` | Действие по запросу пользователя | Разрешить публичный контент |
| Anthropic | `Claude-SearchBot` | Поисковые ответы Claude | Разрешить публичный контент |

Если создаются отдельные группы User-agent, в каждой надо повторить запреты для API, платежей и персональных карт. Специфическая группа может перестать наследовать правила `User-agent: *`. После изменения файл проверяется анализаторами Google и Яндекса и прямыми запросами с соответствующим User-Agent.

### 13.3 Извлекаемость ответа

Каждая важная статья должна содержать короткий прямой ответ сразу после H1: 40-70 слов, которые называют объект, границы и контекст. Следом идёт таблица метода либо проверяемый пример, затем подробное объяснение. Такое построение помогает обычному сниппету, Нейро и системам retrieval-augmented generation выделить законченный фрагмент.

Для темы `Что такое аянамша` сильный начало выглядит так:

```text
Аянамша - угловая поправка между тропическим и выбранным
сидерическим зодиаком. Она меняет долготы планет и лагны,
поэтому два расчёта одной даты могут дать разные положения
у границы знака. VedicWay показывает название аянамши и её
значение рядом с результатом, чтобы карту можно было повторить.
```

После определения страница должна показать формулу или последовательность расчёта, версию используемого стандарта, пример на одной дате, ограничения и источники. Общие фразы о предназначении не дают модели проверяемого утверждения.

### 13.4 Слой доверия для цитирования

GEO-страница VedicWay должна отвечать на шесть вопросов: кто написал; кто проверил; какой метод применён; из какого источника взят факт; когда материал обновлён; что изменит вывод. Эти ответы нужны в видимом HTML. JSON-LD помогает связать сущности, но не заменяет текст.

Для астрологического сервиса особенно ценна граница между расчётным фактом и интерпретацией. Долгота планеты, часовой пояс и выбранная аянамша можно воспроизвести. Смысл дома или даши относится к традиции и требует указать школу. Медицинские, финансовые, юридические и психологические решения нельзя выводить из карты. Такая редакционная дисциплина повышает цитируемость сильнее, чем добавление слов AI или GEO.

### 13.5 `llms.txt`

В репозитории есть базовый `public/llms.txt` с описанием и тремя URL. Формат пока не имеет подтверждённого прямого сигнала ранжирования или цитирования у крупных поисковых систем. Его можно поддерживать как дешёвый навигационный слой, но ставить выше доступного HTML, Sitemap, авторства и источников нельзя.

После публикации файл стоит генерировать из базы и включить: описание сервиса, `/methodology`, `/about`, `/editorial-policy`, четыре хаба, лучшие первичные исследования и дату обновления. Персональные карты, API и платёжные URL туда не попадают.

### 13.6 Панель GEO-измерений

Нужна фиксированная группа из 30 промптов, которую проверяют раз в неделю в Яндекс Нейро, ChatGPT Search, Perplexity, Claude Search и Google AI Mode при доступности. Десять промптов относятся к расчёту, десять - к базовым понятиям, десять - к методике и ограничениям. Для каждого запуска записываются дата, платформа, точная формулировка, присутствие VedicWay, процитированный URL, соседние источники, точность пересказа и факт перехода по доступной аналитике.

Нельзя менять промпты каждую неделю: сравнимость важнее красивого единичного примера. Новые формулировки добавляются отдельной когортой. Первая объективная цель после индексации - получить хотя бы одну корректную ссылку VedicWay в пяти тематических промптах из 30 в течение 90 дней. Это целевой эксперимент, не прогноз.

## 14. Сущность бренда и внешние сигналы

### 14.1 Публичный след

Точный запрос `VedicWay` смешивает российский домен с `vedicway.com` Марианны Полонски и другими организациями Vedic Way. В русской выдаче по сочетанию бренда и натальной карты лидирует `vedicway.com`. Точный домен `vedicway.ru` встречается в низкокачественных агрегаторах доменов, а собственные индексируемые страницы отсутствуют.

Для поисковой системы название, домен, владелец, автор, продукт и контролируемые профили пока не образуют устойчивую сущность. Страница `/about` должна назвать полное обозначение проекта, домен, владельца, продукт, дату запуска, язык и редакционную специализацию. Organization schema использует постоянный `@id`. Те же данные повторяются в реальных профилях и публикациях без вариантов написания, которые создают новые сущности.

Формальный CITE не оценивался: нет Ahrefs, Majestic, Search Console links, ручного списка релевантных конкурентов и подтверждённых санкций. Публичный прокси показывает исходное состояние: брендовых упоминаний почти нет, а независимого тематического консенсуса вокруг `vedicway.ru` не найдено.

### 14.2 Что способно заслужить ссылки

Покупка массовых каталогов не решит конфликт сущностей. VedicWay нужны материалы, на которые ссылаются ради данных или метода. Первая очередь:

| Актив | Содержание | Кому полезен |
|---|---|---|
| Сравнение аянамш на границах | Открытая таблица 100 дат, Lahiri, Raman и True Chitra, версия эфемерид и воспроизводимый расчёт | Разработчики калькуляторов, преподаватели и практики джйотиша |
| История часовых поясов для карты | Проверка города и даты, показ источника временной зоны и предупреждение о спорных периодах | Астрологи и пользователи со старыми датами рождения |
| Карта терминов джйотиша | Связи graha, rashi, bhava, lagna, nakshatra и dasha с первичными источниками | Редакции, студенты и авторы вводных материалов |

Каждый актив получает собственный URL, автора, лицензию, дату версии, CSV или JSON для скачивания и короткое описание методики. Продвижение строится через прямые обращения к авторам тематических обзоров, разработчикам калькуляторов и преподавателям. Анкор и текст публикации определяет независимый автор; обязательный dofollow нельзя ставить условием.

Главная владеет коммерческим калькулятором. Guide строит вечнозелёное обучение. Blog получает материалы с датой: исследования, обновления метода, изменения эфемерид и разборы новых функций. Такая структура отделяет намерения и даёт каждой странице один законченный пользовательский результат.

Каждая статья получает хлебные крошки, ссылку на родительскую категорию, 2-4 контекстных ссылки на соседние шаги и одну ссылку на калькулятор с рабочим якорем формы. Хабы связываются с methodology и example. Footer оставляет только основные legal URL, псевдонимы переводятся 308.

## 16. Аналитика, позиции и контроль изменений

### 16.1 Обязательная настройка

После деплоя надо подключить Яндекс Вебмастер, Google Search Console, Bing Webmaster Tools и Яндекс Метрику с корректным consent-режимом. В Метрике фиксируются события:

| Этап | Событие | Что отвечает на вопрос |
|---|---|---|
| Форма | `chart_form_start`, `chart_form_submit`, `chart_created` | Доходит ли поисковый посетитель до результата |
| Предложение | `paid_offer_view`, `checkout_start`, `payment_success` | Как органический трафик превращается в оплату |
| Контент | `article_50`, `article_source_click`, `article_to_chart` | Читают ли статью и проверяют ли источники |
| Навигация | `site_search`, `filter_use`, `category_click` | Помогает ли архитектура найти материал |
| Ошибки | `api_error`, `article_render_fallback`, `legal_unavailable` | Стирает ли backend-сбой индексируемое состояние |

UTM и технические параметры не должны создавать новые canonical. Директива `Clean-param` в текущем robots полезна для Яндекса, но canonical и серверные редиректы остаются основным контролем дублей.

### 16.2 Панель позиций

Первая когорта - 50 запросов: 10 коммерческих, 20 учебных, 10 методологических и 10 брендовых/навигационных. Позиции снимаются еженедельно в Яндексе по России, Москве и Санкт-Петербургу, а также в Google для русской локали. Записываются URL, позиция, тип результата, SERP feature, конкурент перед VedicWay и изменение после релиза.

Отчёт не должен смешивать частоту Wordstat, показы Search Console и позицию. Wordstat описывает рынок запросов, impressions показывают фактическую видимость сайта, click-through rate - привлекательность сниппета, organic conversion - ценность трафика.

### 16.3 Контентные когорты

Публиковать 202 статьи одновременно нельзя. Первая когорта - 20 лучших материалов: по 5 из каждой категории, без кодировочных дефектов, шаблонных повторов и конфликтов запросов. После четырёх недель сравниваются индексирование, показы, средняя позиция, переходы на калькулятор и источники AI-ответов. Следующая когорта выходит после исправления дефектов, обнаруженных на первой.

Материал обновляется по смысловому событию: изменение алгоритма, источник, новая проверка или исправление. Простая замена даты без видимого изменения запрещена. `dateModified` меняется вместе с журналом правок.

## 18. Порядок работ на 90 дней

### Дни 0-7

Команда исправляет production, сертификат и редиректы; проверяет robots, Sitemap и 404; замораживает массовый импорт. Одновременно чинятся `/chart`, две повреждённые статьи и неподтверждённые цифры на главной. Frontend выбирает модель сохранения серверного DOM и добавляет тест двух стадий рендера.

На седьмой день домен должен стабильно отдавать главную, legal и три тестовые статьи. Поисковые кабинеты подключаются после контрольного crawl, а Sitemap сначала содержит только проверенные URL. Любая 5xx-серия или исчезновение текста после JavaScript возвращает релиз в P0.

### Дни 8-30

Создаются methodology, example, about, editorial policy и страницы авторов. Главная получает поисковый H1, ясную границу бесплатной части и конкретный состав результата. Guide разделяется на четыре категории, источники становятся видимыми. Публикуется первая когорта из 20 статей.

Frontend разделяет пакеты и оптимизирует ресурсы первого экрана. Backend нормализует source JSON, хеширует assets и устраняет повторный запрос статьи. SEO ведёт позиции, coverage, crawl stats и первые 30 GEO-промптов.

### Дни 31-90

Редакция обрабатывает повторы и потенциальную каннибализацию, затем выпускает когорты по 20-30 статей. Порядок определяют реальные impressions и переходы на калькулятор. Команда публикует один первичный ссылочный актив и проводит адресное распространение среди профильных авторов.

На 90-й день оцениваются только измеренные сдвиги: число валидных индексируемых URL, небрендовые показы, доля запросов с правильной посадочной страницей, organic conversion, p75 Web Vitals, видимые citations и упоминания в AI-ответах. Если статьи получают показы без переходов, меняются сниппеты. Если они не индексируются, сначала проверяются качество, повторы и архитектура, а новые материалы не добавляются.

## 19. Definition of Done

### Индексирование

| Проверка | Готово, когда |
|---|---|
| TLS и canonical host | Все варианты домена одним 308 ведут на `https://vedicway.ru`, сертификат валиден |
| Статусы | Публичные страницы 200, удалённые 404/410, псевдонимы один 308, private URL защищены |
| Robots | 200, корректный тип, noindex-страницы доступны роботу, AI-политика утверждена |
| Sitemap | Только canonical 200 URL; количество совпадает с published database |
| Рендер | Основной текст, H1, canonical, robots и JSON-LD одинаковы до и после JavaScript |
| Кабинеты | Sitemap принят Яндексом, Google и Bing; критических ошибок нет |

### Контент

| Проверка | Готово, когда |
|---|---|
| Кодировка | Ни один HTML и JSON не содержит сигнатур mojibake |
| Ссылки | Полный crawl не находит внутренних 4xx и циклических редиректов |
| Источники | Каждый проверяемый тезис имеет видимую опору; schema citation совпадает с HTML |
| Авторство | У каждой статьи есть автор, профиль, дата проверки и способ сообщить об ошибке |
| Повторы | Внутренние повторы объяснены структурой; частые шаблоны переработаны |
| Intent | Один основной кластер и самостоятельный результат на каждый индексируемый URL |
| Публикация | Новая когорта выходит после четырёхнедельной проверки предыдущей |

### Производительность и наблюдаемость

| Проверка | Готово, когда |
|---|---|
| Core Web Vitals | Мобильный p75: LCP до 2,5 с, INP до 200 мс, CLS до 0,1 |
| Ресурсный бюджет | Стартовый JS главной до 100 KB gzip, первый экран до 700 KiB |
| Ошибки | Нет необработанных API-ошибок, которые меняют индексируемый DOM или robots |
| Аналитика | Метрика и поисковые кабинеты получают события без нарушения consent |
| Ранги | 50 запросов проверяются одним методом каждую неделю |
| GEO | 30 промптов проверяются неизменной когортой, сохраняются URL источников |
